# August 2026

## 2026-08-14: Turned three written rules into code that enforces them
**Learned.** I found three rules on the same day that existed only as instructions with nothing checking them, and all three had been failing quietly for days. My job-application workflow wrote a document-sync checklist that no later step ever read back, so exactly two of those checklists existed, every box in them was unticked, and two application folders had gone four days and two days with nothing uploaded. My resume retargeting appended a sentence per application instead of swapping one in, ratcheting my summary from four lines to six with nobody watching the mechanism. A seven-day rule for closing out stale dog-boarding requests had let four of them expire the identical way, $1,227.59 of would-be gross. I made the sync step blocking, put a 525-character hard ceiling with an automated fail on the summary, and rewrote the stale-request rule as a 305-line script that emails me. A rule with nothing enforcing it is a preference, and preferences lose to whatever the system does by default.

## 2026-08-13: Left 13 rows blank rather than invent the numbers
**Shipped.** My job-search tracker had been losing every fit score the moment it was generated: the scoring step produced two numbers, the packaging step never carried them forward, and the tracker columns sat empty. I rewrote the webhook so both scores survive the full pipeline, added a guard so an update can never overwrite a real score with a placeholder, extended the test harness to 56 passing checks, and backfilled 32 historical rows from analysis docs and usage logs, cross-validating two of them against a second independent source. Thirteen more rows I left blank on purpose, because nine of them predate the scoring model entirely and a plausible invented number would have done more damage than an empty cell. In a month I can ask whether my own fit model actually predicts outcomes, which was impossible the day before, and that question only survives contact with the data if every number in the column is real.

## 2026-08-11: Built the health check outside the system it watches
**Shipped.** Eight days earlier an OAuth revocation took down five of my automations plus all three alert paths that were supposed to tell me, because every one of them authenticated through the same grant. The fix is an unauthenticated probe that runs as the very first step of my morning job runner, ahead of anything that needs a token: it hits each script's public endpoint, writes an on-disk sentinel, fires a desktop notification, and clears itself on the next clean run. I verified it against eight cases, including the one that actually matters, where a revoked script returns HTTP 200 with a body reading "Access Denied" and a naive status-code check calls that healthy. It caught a real failure 19 hours after I installed it. A monitor is worth only what it can still detect once the thing it watches is broken, so build it out of fewer moving parts than the system it guards.

## 2026-08-10: Lost pipeline history to my own agents writing in parallel
**Learned.** Several of my automated sidekicks ran at the same time and each rewrote one shared state file from its own stale read. The merged result looked like a complete history while quietly missing roughly 16 companies of pipeline detail and two entire sections, and with no git history and no backup on that file, none of it was recoverable by rollback. I rebuilt what could be reconstructed from the tracker sheet and the folders on disk, then wrote a header at the top of the file naming exactly what is gone for good, so no future reader mistakes a thin record for a quiet month. Three guard scripts followed (an append-only check on the logs, a scheduled backup, an integrity check on the state files) plus one rule pushed across 24 agent definitions: any process writing shared state has to make its own incompleteness visible at the point where someone would act on it. This was the third time this failure shape had bitten me, and the first two cost me nothing I could see, which is exactly why it got a third turn.

## 2026-08-09: Repaired the tool that had been measuring my week wrong
**Learned.** My daily recap system reported ApplyTrue as dormant for five weeks while I was in the middle of pushing the most code I have written all year. Two shell bugs caused it: the repo scan used a depth limit of three directories and that repo sits at depth seven, and the scan loop broke on a folder name containing a space. Both are boring on their own, and together they made every report confidently wrong in the same direction. I patched the scanner, wrote the rules into the runbook so the same shortcut cannot come back, rebuilt the two missing daily files, and re-sent the weekly summary with a correction banner on it. A measurement tool that under-reports quietly is worse than having no measurement at all, because it teaches you the wrong lesson with a straight face.

## 2026-08-08: Shipped a billing system with its own off switch
**Shipped.** Built ApplyTrue's paid-plan billing in a single day, 17 commits across nine merged pull requests, with a feature flag wired in from the first commit so the whole thing can be turned off without a deploy. Then I ran an adversarial QA pass against my own work, and it found seven critical bugs, all fixed before anything went near a real card. The deduplication work that same day took three passes to land: a first cut, a redesign after QA showed it merging records that were genuinely different, and a hardening round after an adversarial re-review. On anything that charges money or silently eats user data, the kill switch and the second reviewer belong in the same commit as the feature.

## 2026-08-05: Audited the sources instead of the outputs
**Learned.** My job-application pipeline runs an automated check on every generated resume and cover letter before I ever see it, and that check has never once looked at the template files those documents are generated from. I read the sources directly and found four stale facts sitting in them: an out-of-date dollar figure in two templates, a volunteer role written as ongoing after it had ended, a broken table row, and a management tenure number that contradicted my own verified record. All four had been propagating into finished applications, and none of them could have been caught downstream, because the checker has no way to know what "correct" means at that layer. Verification that only runs at the end of a pipeline will confidently pass work that was already wrong when it started.

## 2026-08-04: Chose a slower pipeline over a faster wrong answer
**Decided.** My job-application workflow was running 26 minutes against a 5-minute target, so I ran a postmortem on where the time actually goes. Most of the proposed speedups held up: a cheaper model for the first draft, parallel fix rounds, a hard cap of one revision loop. I rejected one. Surfacing drafts the moment the automated checks pass, and letting the independent review land as a trailing follow-up, would have put a fabricated job title in front of me formatted as my own resume, because the mechanical checks validate length and keywords but never titles. Speed work stays worth doing right up until it moves a correctness check behind the thing that check exists to protect.

## 2026-08-03: My monitoring failed at the exact moment I needed it
**Learned.** Google revoked the OAuth grant on every Apps Script project on my account overnight and five automations went dark at once. The purpose-built watchdog I wrote to catch exactly this class of failure was one of the five, because it shipped its alerts through the same authorization it was supposed to be watching. So did the dead-man's switch backstopping the watchdog. So did the per-job failure alerts. Three independent safety nets, one shared dependency, three silent days before I noticed on my own. The lesson cost me a long weekend of automation: a monitor that lives inside the failure domain it watches isn't monitoring anything.
